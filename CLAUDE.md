# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A small shared to-do app with named lists: FastAPI + SQLite (stdlib `sqlite3`, no ORM) + a React + TypeScript page (built by Vite), in one Docker container. AI agents (Claude, Gemini) connect to it as an MCP server at `/mcp`, signing in through Taskly's own OAuth. It runs on the same VM as the Reels app (`C:\Project\ReelsTranslator`), behind that VM's shared Caddy. README.md covers running, the API, the database and deploying.

## Commands

The dev machine is Windows; use the venv's interpreter.

```powershell
.venv\Scripts\python.exe -m pytest                                   # API tests, under a second
.venv\Scripts\python.exe -m pytest tests/test_tasks.py::test_delete    # one test
npm --prefix frontend test                                           # page logic tests (Vitest)
npm --prefix frontend run build                                      # typecheck + build into taskly/static/
npm --prefix frontend run icons                                      # remake the PWA icons in frontend/public/ from icon.svg
.venv\Scripts\python.exe -m uvicorn taskly.main:create_app --factory --reload   # API on :8000, reads .env
npm --prefix frontend run dev                                        # page on :5173, proxies /api to :8000
.venv\Scripts\python.exe -m taskly.admin add-user me                  # a local account, needed to use the page
docker compose up -d --build                                         # http://localhost:8001; needs `docker network create web` once
.\scripts\deploy.ps1                                                 # deploy the last commit on main
```

Node ≥ 22.12. No linter or formatter is configured.

## Architecture

- **App factory.** `create_app(settings=None)` in `main.py` runs `db.migrate`, adds `routes.router`, `oauth_routes.router` and the `/mcp` route, and mounts `settings.static_dir` at `/` last (so API routes win; `html=True` serves `index.html`), only if that folder exists: without a build the API still runs. Tests pass their own `Settings`; `make_settings` points `static_dir` at an empty tmp folder. HTML answers get `Cache-Control: no-cache` (index.html names the build's hashed files).
- **Database.** `db.py`: `connect()` sets `row_factory`, foreign keys and a busy timeout; `migrate()` sets WAL and applies `MIGRATIONS[user_version:]`, each as one `executescript` transaction that also bumps `PRAGMA user_version`. **Only append to `MIGRATIONS`; never edit or reorder a deployed one.** Each request gets its own connection (`deps.get_db` → `db.session`). The schema is drawn in `docs/data-model.html` from its `MODEL`; `docs/data-model.svg` (in the README) is that page's "Copy the diagram as SVG". Update both with every migration.
- **Accounts.** `passwords.py` (scrypt, at most 4 at once for memory), `users.py` and `sessions.py` are plain queries; `auth.py` is the FastAPI side: the `taskly_session` cookie, `CurrentUser` (every `/api` route but login and logout uses it), the login throttle (in memory, one process; checks and reserves each attempt under a lock, so parallel guesses can't pass the limit) and a middleware that refuses cross-site writes (`Origin` ≠ `scheme://host`), sets `Cache-Control: no-store` on `/api` and renews the cookie. Accounts are made with `python -m taskly.admin`; there is no sign-up. `deps.py` holds `get_db`/`Conn`. Endpoints return `None` with `status_code=` in the decorator, never a `Response` object: FastAPI drops cookies set on the injected `response` otherwise.
- **Queries** live in `users.py`, `sessions.py`, `lists.py`, `tasks.py` and `snapshot.py` and return plain dicts (`status` as `new`/`progress`/`done` plus `done` as a bool, people as usernames). Tasks sort not done first, then the ones with a due date, soonest first (a time is its moment; a date alone counts as the end of that day: UTC's in `tasks.list_tasks`, which sorts in Python since SQLite knows no zones, and the device's in `view.sortTasks`), then oldest first; `view.sortTasks` sorts the same way. Routes stay thin: validate with pydantic (`Title`, `ListName` strip and bound length; ids are `UUID`), check the role with `require_role`/`task_for` (none → 404, member doing an owner's action → 403), call the queries.
- **Repeating tasks.** `tasks.repeat` is a rule in a small part of iCalendar's RRULE plus our `FROM=DONE` (`repeats.py`, which has the format), stored canonical with the parts left out taken from the due date, so a task on the 31st stays on month ends. Finishing one in `tasks.update_task` makes the next task in the same transaction (`BEGIN IMMEDIATE`, so reading the old status and writing can't race) and moves the rule to it: a series has one repeating task, and reopening the finished one leaves both and makes nothing more. Every failure in `repeats.py` must be a `ValueError` (a 422), never another error: a 500 holds the page's whole queue. `repeats.py` and the page's `repeat.ts` work out the next day alike and are both tested on `frontend/src/repeat.cases.json`: add cases there.
- **Lists.** Every list has an owner, who is also a member row. `GET /api/sync` is the only read endpoint for lists and tasks. Task ids are UUIDs made by the page; `POST /api/tasks` with an existing id in the same list is a retry and answers 200 unchanged.
- **Old pages talk to new servers.** A phone can come online with changes queued by an older version of the page and send them before it loads the new one. Keep `POST/PATCH/DELETE /api/tasks` accepting what they accept today: add optional fields (`PATCH` took `status` in schema 5; `done` is still accepted and answered, and `done: false` reopens only a done task; `POST` and `PATCH` took `due_date` in schema 6, where a field left out leaves it alone and `null` removes it, so `PATCH` checks `model_fields_set`, and with it `due_time` and `due_zone` in schema 7: a `due_date` replaces the due date with its time, and time and zone come only with their date; `POST` and `PATCH` took `notes` in schema 8: left out stays, `null` or `""` removes them; and `repeat` in schema 9, the same way, where removing the due date removes it too and a `due_date` alone moves a rule taken from the old date, with `PATCH`'s `next_id` and `finished_on`, sent when it finishes a repeating task: left out, the server picks a new id and its own today); don't rename or remove fields or endpoints the queue uses. A change the server can't apply must answer 404, 409 or 422 (the page drops it with a note), never 5xx (the page would retry it forever).
- **Frontend** (`frontend/`). React + TypeScript, built by Vite into `taskly/static/` (gitignored; the Docker image builds it in a Node stage). Three screens behind tabs: List, Board (New / In progress / Done; on a desktop cards also drag between columns, native HTML5 drag and drop, while phones keep the buttons) and Focus (a pomodoro timer, `timer.ts`, kept only in the device's localStorage, with the task focused on, picked there or with a task's timer button, and the focus sessions counted per task). Due dates (`due.ts`, `DuePicker.tsx`) are calendar days compared with the device's date, never the server's: chips on the List and Board (overdue, today, tomorrow), set from the List's calendar chip, and the List's "Due today" filter (overdue included; a task added while it's on is due today). "Tomorrow" without a time typed means noon tomorrow, in the device's zone. An optional time is a clock time in the zone of whoever set it (`due_zone`, checked server-side with `zoneinfo`; `tzdata` in requirements because Windows has no zone database): one moment, which `instantOf` works out with `Intl` and every device shows in its own time, noting the setter's time when it reads differently; a timed task is overdue once that moment passes. `due.test.ts` switches `TZ` (`vi.stubEnv`) to check Florida against the Canaries. Notes (`notes.ts`, `TaskNotes.tsx`; not `Notes.tsx`, which would clash with `notes.ts` on Windows' case-blind disk) are plain text: two lines under the title on the List and on Board cards, `http(s)` addresses as links (only those, so a note can't make a `javascript:` link), edited in a row under the task like the due date picker; the add bar's notes button gives a new task its notes. Repeats (`repeat.ts`) are set in the due date picker (choices named after the date, or Custom), which sends the task's own rule unchanged unless the date or the repeat changed; a repeating task's chip has the repeat mark. Every status change goes through `stages.statusChange`, which adds `next_id` and `finished_on` when it finishes a repeating task, so `applyQueue` shows the next task offline under the id the server will give it. The header's magnifier opens search over the screen (`search.ts`: every list, titles and notes, on the device's copy). The look is the "Organic" design (a design handoff, option 1b, October 2026): its tokens are the variables at the top of `style.css` (plus a dark palette of our own), Archivo comes from `@fontsource/archivo` and icons from `lucide-react` (both bundled; the service worker precaches the fonts). Desktop layout from 900px: sizes switch in `style.css`, structure via `useWide`. `src/api.ts` and `src/sync.ts` (the queued task changes and `/api/sync`) are the only places that call `fetch`; `api.ts` throws `ApiError` with the server's `detail`. The page draws from the device's copy: `store.ts` (IndexedDB: the last `/api/sync` answer and a queue of unsent task changes), `view.ts` (`applyQueue`: pure, what the screen shows), `sync.ts` (sends the queue in order, then downloads `/api/sync`; one at a time). Task changes go into the queue, then the page redraws from the local copy and syncs; list and member changes call the API directly and need a connection. `device.ts` holds the page's one `store` and `sync`. `vite-plugin-pwa` makes the manifest and service worker (it never handles `/api`). No `alert`/`confirm`: confirmations are inline. Keep all assets local: no CDNs or other sites. The dev server's proxy must not use `changeOrigin`, and so not Vite's string shorthand (`"/api": "http://…"`), which turns it on.
- **AI agents (MCP).** `/mcp` (`mcp_server.py`) is the `mcp` SDK (2.x, `MCPServer`; stateless, JSON answers; serves both the 2025 `initialize` protocol, which Claude uses, and 2026-07-28) behind our own ASGI `Guard`: it refuses a foreign `Origin`, needs `Authorization: Bearer` (else 401 with `WWW-Authenticate: Bearer resource_metadata=…`), checks the token is for `{site}/mcp`, and puts the user in a `ContextVar` that the tools read. The SDK's own auth (`AuthSettings`, `TokenVerifier`) and its OAuth server provider are not used. `/mcp` is added with `app.add_route` (exact path; a mount would redirect to `/mcp/`), before the static mount. The SDK's session manager runs in the app's lifespan (`mcp_server.running`), which makes a new one on each start since one can only run once; a second `with TestClient(app)` on the same app would replace it, so tests use a second client without `with` when the first one talks to `/mcp`. The tools (`list_lists`, `list_tasks`, `create_list`, `rename_list`, `delete_list`, `add_tasks`, `complete_task`, `set_task_status`, `update_task`, `delete_task`, `clear_done`) reuse the queries and have the page's rights (members aren't the agents' job); failures are `ToolError` (an `isError` result), never HTTP errors. **Agents keep the tool names and arguments: add optional arguments, don't rename or remove** (`add_tasks` still takes `titles`, `update_task` a `title` alone). The SDK fills in defaults and can't tell an explicit `null` from a missing argument, and some clients send `null` for every optional one, so for agents `null`/missing leaves a field alone and `""` clears it (`update_task`'s `notes`, `due_date` and `repeat`), unlike the API's PATCH; don't "fix" that. `complete_task` and `set_task_status` answer with `next` when they finished a repeating task, and take an optional `today`, the user's date (the server's is UTC's, a day ahead in the evening west of UTC). Rules on arguments go in their types (`add_tasks`' items are `NewTask(Due)`, inlined with `WithJsonSchema` because some clients don't follow `$ref`): a pydantic `ValidationError` raised in a tool's body reaches the agent as a bare "Error executing tool"; checks in the body raise `ToolError` (`routes.due_problem` gives both the API and the tools the due date's rules).
- **OAuth for agents.** Taskly is its own authorization server (`oauth_routes.py`, queries in `oauth.py`, the HTML in `oauth_page.py`): discovery (`/.well-known/oauth-protected-resource[/mcp]`, `/.well-known/oauth-authorization-server`), open dynamic registration (`/oauth/register`), the sign-in and Allow page (`/oauth/authorize`), and `/oauth/token` (PKCE S256 only, public clients, a `resource` on every code, single-use codes, refresh tokens replaced on use). The site's address comes from the request (`scheme://host`, like the Origin check), so there is no setting. Registration is open, so `oauth.redirect_allowed` is what keeps codes from being phished: only Claude's and Gemini's callbacks and loopback (any port, RFC 8252). CIMD isn't advertised (it would make the server fetch URLs clients name). The page signs in with the same throttle as `/api/login` but makes no browser session. These routes return `Response` objects (none sets a cookie). The page sends `Referrer-Policy: same-origin` (with `no-referrer` browsers post the form with `Origin: null`, refused), `frame-ancestors 'none'`, and no CSP `form-action` (Chrome applies it to the 303 to the agent). The auth middleware's Origin check also covers `POST /oauth/authorize`, and `no-store` covers `/oauth/` and `/.well-known/`. A password change, `reset-password`, `disable-user` and `revoke-sessions` call `oauth.delete_user_grants`. The service worker's `navigateFallbackDenylist` must keep `/oauth/`, `/mcp` and `/.well-known/` (else an installed PWA shows the page instead of the sign-in).
- **Settings** (`settings.py`) read the environment and `.env` in the working directory. So far `DB_PATH`, `STATIC_DIR` (the built page) and `API_DOCS` (FastAPI's `/docs`, `/redoc`, `/openapi.json`; off by default and on the VM, since the site is public).

## Deployment (shared VM)

The VM runs one Caddy (`~/proxy`, owns 80/443) and several apps, each its own Compose project in its own folder. Things that must stay true:

- **`~/taskly` is the only thing a deploy touches.** Never add steps to `deploy.ps1` that restart Caddy, touch `~/proxy`, or run compose outside `~/taskly`. The Caddyfile block for this site is added by hand (README, "First deploy").
- **The alias is `taskly`, the host port is 8001.** `docker-compose.yml` joins the external network `web` with alias `taskly`, which Caddy uses (`reverse_proxy taskly:8000`). Aliases must be unique across apps on `web`. Reels already binds `127.0.0.1:8000` on the VM, so this app's host port is `127.0.0.1:8001`. Never publish a port on `0.0.0.0`.
- **`name: taskly` in `docker-compose.yml`** pins the Compose project name, so it doesn't depend on the folder a clone lives in.
- **Data lives only in `./data` (mounted at `/data`).** Anything written elsewhere in the container is lost on the next deploy.
- **The VM's IP and host name are never committed.** `deploy.ps1` reads them from `scripts/deploy.local.psd1` (gitignored; template `deploy.local.example.psd1`), handed over with the SSH key on a USB stick. Docs use `<site>` and `<vm-ip>`.
- **`deploy.ps1` ships the last commit via `git archive`**, not the working tree. On the VM it first removes every top-level entry of the archive from `~/taskly` (never `data/` or `.env`), then unpacks: unpacking over the old copy left files deleted in git behind, and the phase 2 deploy's build failed on a stale `TodoItem.tsx`. Then it builds, backs up (`python -m taskly.backup`), migrates (`python -m taskly.migrate`), then runs `docker compose up`. Backup and migrate run as `docker run --rm --network none … taskly-app`, never `docker compose run`: a compose one-off container joins `web` with alias `taskly` and could receive Caddy's traffic. It sets TLS 1.2 explicitly because Windows PowerShell 5.1 doesn't offer it by default.
- **The app does its own logins** (phase 1b). The site's Caddyfile block is only `reverse_proxy taskly:8000`; never add `basic_auth` back. README "Caddy: the address" is the how-to for the address and Caddy errors; keep it current when giving Caddy instructions.
- **The per-IP login throttle trusts uvicorn's `--forwarded-allow-ips=*`**, i.e. the leftmost `X-Forwarded-For`. That is safe only because Caddy replaces `X-Forwarded-For` from untrusted clients (its default). Never give the shared Caddy `trusted_proxies` or put a CDN in front without revisiting this.
- **`/health` touches the database**, so a broken volume fails the deploy check instead of the first request.
- **Agents need nothing from Caddy.** `reverse_proxy taskly:8000` passes `/mcp`, `/oauth/` and `/.well-known/`. The address agents are given is `https://<site>/mcp`; the discovery documents take the address from the request (Host and `X-Forwarded-Proto`), so Caddy must keep passing the original Host (its default).

## Things we learned

### Caddy on the shared VM (found on the first deploy)
- **`caddy` exists only inside the container.** Every Caddy command is `docker compose exec -w /etc/caddy caddy caddy <command>`, run in `~/proxy`. Without `-w /etc/caddy`, `reload` looks in the container's working directory `/srv` and fails with "no config file to load"; that is how the first reload silently never happened, and the browser showed `ERR_CONNECTION_CLOSED` (Caddy had no block for the name).
- **Always `validate` before `reload`.** Caddy is shared with Reels. A failed reload is safe (Caddy keeps its running config), but a bad config that validates would hit both sites.
- **The Caddyfile is a read-only single-file bind mount.** `caddy fmt --overwrite` can't run in the service container; use `docker run --rm -v ~/proxy/Caddyfile:/etc/caddy/Caddyfile caddy:2 caddy fmt --overwrite /etc/caddy/Caddyfile`. An editor that replaces the file (new inode) leaves the container on the old copy until `docker compose up -d --force-recreate caddy`. `nano` writes in place. The "Caddyfile input is not formatted" warning is harmless.
- **The real site name stays out of the repo** like the VM's IP: docs say `<site>`; it lives in `deploy.local.psd1` and `~/proxy/Caddyfile`.

### MCP connector (found on its first deploy, October 2026)
- **claude.ai connected on the first try** with dynamic registration and no client secret; it sends no `Origin` to `/mcp`, so `Guard`'s check is fine. Check after a deploy: `/.well-known/oauth-authorization-server` must say `"issuer": "https://<site>"` (https comes from Caddy's `X-Forwarded-Proto` and uvicorn's `--proxy-headers`).
- **Google Safe Browsing flagged the site as phishing** ("Dangerous site" in Chrome and Safari) right after the deploy: a password form on a free dynamic-DNS name, and the sign-in page names "Claude (claude.ai)". Only browsers are affected (the sign-in tab, the page); Claude's server calls are not. Lifting it is a Search Console review (README, "Talking to it from Claude"); a domain of our own is the lasting fix.

### App
- **Windows PowerShell 5.1's `Get-Content`/`Set-Content` read files in the ANSI code page**, so rewriting a UTF-8 source with them garbles its non-ASCII characters: `TaskItem.tsx`'s "·" shipped as "Â·" (October 2026). Edit with the editor tools, or Python with explicit UTF-8; `frontend/src/encoding.test.ts` checks the page's sources.
- **On Windows, `mimetypes` can map `.js` to `text/plain`** from the registry, and browsers then refuse the module script. `main.py` forces `text/javascript`; `test_page_and_its_files_are_served` guards it.
- **`Settings` reads `.env` from the working directory.** Tests build settings with `tests/conftest.py::make_settings(tmp_path)`, which passes `_env_file=None`. Use it.
- **Tests log in.** The `client` fixture is logged in as `maria`; `anon` isn't. `fast_passwords` (autouse) lowers scrypt's cost; `test_passwords` checks the real one. `conftest.connect_agent(client)` does what Claude does (register, sign in on the page, swap the code) and returns the tokens; `tests/test_mcp.py` speaks raw JSON-RPC to `/mcp` with them.
- **The MCP SDK's own OAuth client is the best end-to-end check.** `OAuthClientProvider` plus `Client(streamable_http_client(url, http_client=...))` against a running uvicorn does what a real connector does (401 → discovery → registration → sign-in → token → tools); a `redirect_handler` can post the sign-in form itself. The browser check of the sign-in page found the `Origin: null` bug that `TestClient` can't (it sends no Origin).
